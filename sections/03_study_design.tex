\section{Study Design}

We designed a controlled study to isolate how the composition of inference-time Self-Refinement affects code correctness and token consumption.
For each model and task, all variants used the same self-generated initial candidate and no execution feedback.

\subsection{Research Questions}

\researchquestion{RQ1}{How does the composition of Self-Refinement affect final code correctness?}
An explicit critique or revision plan may help a model review its candidate, but each additional step is useful only if it leads to a better final program.
We isolate these contributions by successively comparing revision alone, revision guided by a self-generated critique, and revision guided by both a critique and an explicit plan while holding the initial candidate fixed.

\researchquestion{RQ2}{How do alternative refinement approaches balance repairs of initially incorrect candidates and regressions of initially correct candidates?}
A net change in pass rate can conceal whether refinement repairs many failures while also damaging programs that were already correct.
We therefore compare the initial and final programs for each task and measure how often refinement repairs a failure, introduces a regression, or preserves the initial correctness outcome.

\researchquestion{RQ3}{How does the value of selectively applying refinement vary across model-benchmark combinations with different initial pass rates?}
Selective refinement can protect candidates that do not need revision, but an incorrect preservation decision can also forgo a possible repair.
We examine how the model's decision to preserve or revise each initial program changes correctness and token use across model-benchmark combinations with different initial pass rates.

\researchquestion{RQ4}{Do the correctness effects of additional refinement steps justify their token costs?}
Critique, planning, and selection require additional inference even when they do not improve the final program.
We compare the resulting correctness changes with added token use at the candidate and benchmark levels, including the tokens avoided when refinement is not applied.

\subsection{Self-Refinement Protocols}

For each model-task pair, Direct Generation produced one Initial Candidate from the Task Specification.
The candidate was stored once and reused as the exact input to every refinement variant, so differences between variants did not arise from different initial generations.
We refer to this control as the Shared-Initial Design.
Benchmark execution was reserved for evaluation and provided no feedback to the model.

We decomposed refinement into four observable Refinement Stages: Refinement-Need Decision (\texttt{D}), Critique Generation (\texttt{C}), Revision Planning (\texttt{P}), and Code Revision (\texttt{R}).
Each stage was a separate prompt and model call with a stored output artifact, rather than an inferred internal reasoning step.
This separation lets us add one explicit operation at a time, reuse the same upstream artifact in downstream variants, and attribute token consumption to the calls that produced it.

The three Always-Refine Protocols are named by their execution order.
Direct Revision (\texttt{R}) performs Code Revision without an upstream artifact, Critique-Conditioned Revision (\texttt{CR}) supplies a stored critique artifact to Code Revision, and Critique-and-Plan-Conditioned Revision (\texttt{CPR}) inserts Revision Planning between Critique Generation and Code Revision.

Direct Revision provides the least structured refinement condition.
Its single call must inspect the Task Specification, decide whether the Initial Candidate has a functional problem, and produce the complete Revised Candidate.
It therefore serves as the reference point for asking whether externalizing intermediate work changes the outcome, rather than as a condition with no review.

Critique Generation separates diagnosis from code production.
Given only the Task Specification and Initial Candidate, the model was asked to identify potential functional mismatches and relevant fault locations, or to recommend preservation when it found no problem.
The prompt prohibited a complete revised solution and a completed revision plan, so the resulting critique artifact records what may be wrong without asking the same call to implement the correction.
Code Revision in \texttt{CR} then receives this stored artifact as guidance.

Revision Planning tests whether an additional translation from diagnosis to an actionable edit strategy benefits revision.
A critique may identify a defect without specifying which behavior should change, which parts should remain intact, or how multiple changes should be ordered.
The Planning call therefore receives the Task Specification, Initial Candidate, and stored critique artifact and is asked to state the changes and relevant locations without producing a complete solution.
We place Planning only after Critique Generation because a plan generated without a critique would combine defect identification and planning in one call and would not isolate the same intermediate operation.
This stage may also propagate an incorrect critique or add cost without improving the code; accordingly, the \texttt{CPR} versus \texttt{CR} comparison measures the net effect of the Planning call, its artifact, and its token consumption rather than the intrinsic quality of plans in isolation.

Code Revision is the only Refinement Stage that produces executable code.
Every Revision call receives the Task Specification and exact Initial Candidate; \texttt{CR} additionally receives the critique artifact, and \texttt{CPR} receives both the critique artifact and revision plan.
All three templates permit the model to retain the candidate when no functional change is needed and require exactly one complete fenced Python block as output.
No stage receives tests or execution feedback.

Refinement-Need Decision is independent of the intermediate refinement artifacts.
It receives only the Task Specification and Initial Candidate and returns \texttt{PRESERVE} or \texttt{REFINE}, without generating a critique, plan, or code.
When the Decision is \texttt{PRESERVE}, the Final Candidate is the exact stored Initial Candidate; when it is \texttt{REFINE}, the Final Candidate is the Revised Candidate produced by the matched \texttt{R}, \texttt{CR}, or \texttt{CPR} sequence.
This construction yields Decision-Conditioned Direct Revision (\texttt{DR}), Decision-Conditioned Critique-Conditioned Revision (\texttt{DCR}), and Decision-Conditioned Critique-and-Plan-Conditioned Revision (\texttt{DCPR}) without additional revision calls.
The same Decision was reused for all three outcomes and received neither the later intermediate artifacts nor the identity of the sequence whose outcome it selected.

The incremental comparisons concern complete Stage Compositions.
Thus, \texttt{CR} versus \texttt{R} measures the combined effect of the Critique Generation call, its artifact, and its token cost, while \texttt{CPR} versus \texttt{CR} measures the corresponding combined effect of Revision Planning.
We do not interpret either contrast as an independent evaluation of critique or plan correctness.

We selected HumanEval+, MBPP+, and BigCodeBench-Instruct to cover complementary Python task settings rather than treating the benchmarks as fixed difficulty categories.
HumanEval+ and MBPP+ provide function-level tasks with different specification styles, whereas BigCodeBench-Instruct adds broader library use and compositional requirements.

Initial Pass Rate was treated as an observed characteristic of each of the 18 model-benchmark combinations.

\subsection{Experimental Setting}

To reduce model-loading and duplicate-call costs, we executed the experiment by model-resident phase rather than running each task through every protocol end to end.
For each checkpoint, we first completed Direct Generation for all 1,677 tasks, then generated all \texttt{D} decisions, \texttt{R} candidates, \texttt{C} artifacts, \texttt{CR} candidates, \texttt{P} artifacts, and \texttt{CPR} candidates in dependency order.
The stored Critique was reused by \texttt{CR} and \texttt{P}, the stored Plan was reused by \texttt{CPR}, and one Decision was reused to derive \texttt{DR}, \texttt{DCR}, and \texttt{DCPR}.
Immutable artifacts were checkpointed at phase boundaries so completed logical calls could be resumed without regeneration.

All inference ran on an Ubuntu 22.04 server with two 24~GiB NVIDIA GeForce RTX 4090 GPUs.
We used vLLM 0.26.0 with tensor parallelism of two, a batch size of 32, a 16,384-token context limit, and GPU memory utilization of 0.85.
Prompts used each checkpoint's tokenizer and chat template, automatic prompt truncation was disabled, and every rendered prompt was required to fit the common context limit together with its output allowance.
Generation used batch-invariant greedy decoding with one output, temperature 0, top-$p$ 1, seed 0, and all penalties disabled.
Maximum output lengths were 4,096 tokens for candidate generation, 2,048 for Critique and Plan, and 64 for Decision.

We applied a strict output contract to every generated candidate.
The response had to contain exactly one complete fenced Python block; otherwise, no candidate was extracted or repaired.
Across 70,386 executed model calls, eight Direct Generation responses and ten revision responses violated this contract and were retained as \texttt{malformed\_candidate}; the eight malformed Initial Candidates blocked their 48 dependent calls.
These cases remained in the study scope and counted as zero only for end-to-end success, while functional transitions were left unavailable because no candidate was executed.

Decision responses were parsed only when the complete trimmed response was \texttt{PRESERVE} or \texttt{REFINE}.
Among 202 non-exact responses, 156 differed only by one terminal period and were normalized deterministically, while 46 unambiguous explanations were coded before candidate evaluation under a fixed execution-blind rubric.
All 202 responses were resolved, their original status and token counts were retained, and exact-parsed Decisions were analyzed separately as a sensitivity check.

We evaluated Initial and Final Candidates in processes separated from model inference, and a candidate passed only if it satisfied the benchmark's full test suite.
HumanEval+ and MBPP+ used EvalPlus 0.3.1 in the Python 3.12 environment also used for orchestration and analysis.
BigCodeBench-Instruct used a separately pinned Python 3.10.12 environment compatible with its official dependency range.
Candidate execution was isolated from the host process namespace and external network, and EvalPlus candidates had an 8~GiB process-memory limit.

We fixed task-level timeouts before model inference by running each official reference solution three times in its final evaluator environment.
The default primary limit was 10 seconds; \texttt{Mbpp/599} used 60 seconds, and 15 BigCodeBench tasks used limits from 30 to 240 seconds.
After the complete primary batch, a provisional timeout was retried once using the larger of 120 seconds and 1.5 times its primary limit; \texttt{HumanEval/38}, \texttt{/50}, and \texttt{/53} used a pre-specified 180-second confirmation limit.
A candidate was assigned final \texttt{TIMEOUT} only when both attempts timed out.

The analysis paired every evaluable Initial Candidate with the Final Candidate selected by each protocol.
We reported Initial and Final Pass Rates and decomposed their difference into Repair, Correct-to-Incorrect Regression, Functional Preservation, and Unrepaired Failure.
Protocol comparisons used a task-level paired bootstrap with 10,000 resamples, a fixed seed of 20260804, and 95\% confidence intervals.
Token cost was computed from the calls required by each protocol; a Decision-Conditioned protocol included only the Decision cost after \texttt{PRESERVE} and added the corresponding Always-Refine cost after \texttt{REFINE}.
