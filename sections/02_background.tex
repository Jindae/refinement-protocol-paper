\section{Background}

\subsection{Self-Refinement without Execution Feedback}

Self-Refinement extends one-step generation by asking a large language model (LLM) to inspect and improve an output after it has been produced.
Self-Refine established a general inference-time pattern in which the same model generates an initial output, produces natural-language feedback, and revises the output without additional training or supervised refinement data \cite{madaan2023selfrefine}.
This pattern is the closest conceptual basis for Critique-Conditioned Revision in our setting because the critique artifact is generated by the model that also performs Code Revision.
However, Self-Refine applies an integrated feedback-and-revision loop across diverse tasks rather than isolating the incremental effect of Critique Generation on shared initial code candidates.

Recent work has examined critique artifacts more directly.
RCO trains a critic by rewarding critiques according to their downstream refinement utility, including on code generation tasks, rather than according to surface-level critique quality \cite{yu-etal-2025-training}.
This result supports evaluating a critique through the revised candidate it enables, but RCO concerns critic training rather than a controlled comparison of separate inference-time Refinement Stages.
SCOPE structures a code critique around subgoals, gap analysis, and robustness checks before using it for revision \cite{zhang2026scope}.
Its structured critique is closely related to the role of Critique Generation in this study, although it uses a learned critic and execution-based rewards rather than comparing Direct Revision, Critique-Conditioned Revision, and Critique-and-Plan-Conditioned Revision with a fixed model.

Another line of work treats self-correction as a capability to be learned.
SCoRe uses multi-turn reinforcement learning to improve self-correction without external evaluator feedback at inference time and evaluates the learned behavior on HumanEval as well as mathematical reasoning \cite{kumar2025score}.
It demonstrates that intrinsic correction can be trained, but its integrated correction policy does not expose the contribution or token cost of separate critique and planning calls.
CoCoS trains small code models to preserve correct outputs while progressively correcting incorrect ones and explicitly distinguishes incorrect-to-correct repairs from correct-to-incorrect regressions \cite{cho-etal-2025-self}.
It is therefore particularly close to our transition analysis, but its objective is to learn a correction-preserving policy rather than compare prompting protocols applied to the same initial candidate.
ReflexiCoder learns trajectories containing initial code, reflection, and corrected code, enabling inference-time correction without an execution engine \cite{jiang-etal-2026-reflexicoder}.
Its feedback-free setting is also closely related, although the trajectory is internalized through training instead of being decomposed into separately observed Refinement Stages.
ReVISE jointly develops intrinsic self-verification and reasoning correction and allows the model to decide whether further refinement is needed \cite{pmlr-v267-lee25ab}.
This refine-or-stop behavior motivates selective refinement, but it remains embedded in a trained procedure rather than operating as a standalone decision that exactly preserves an initial code candidate.

Related studies provide more indirect evidence for decomposing critique and revision.
Code Reffix evaluates reflection generation and reflection-guided repair as distinct capabilities, CodeReviewQA separates review comprehension into change recognition, localization, and solution identification, and COAST organizes debugging data around component abilities such as localization, identification, and repair \cite{di-etal-2026-code,lin-etal-2025-codereviewqa,yang-etal-2025-coast}.
These studies show that intermediate artifacts and component abilities can be examined separately, but they focus on benchmark design or training rather than cumulative inference-time Stage Composition over a self-generated Initial Candidate.

\subsection{Execution-Guided Refinement and Staged Workflows}

Much of the code refinement literature obtains a correctness signal by executing a candidate.
Teaching Large Language Models to Self-Debug combines natural-language explanation with unit-test or execution results in iterative debugging and also considers explanation when tests are unavailable \cite{chen2024selfdebug}.
The study demonstrates that explanation can support revision, but its principal code-generation conditions can expose candidate behavior directly to the model.
This feedback boundary is important because tests in the present study determine Functional Correctness only after generation and are never supplied to the model.

Execution feedback has been incorporated into both editing systems and model training.
Self-Edit gives a fault-aware editor the outcomes of example-test execution, while CYCLE uses execution feedback to train small code models for iterative refinement \cite{zhang-etal-2023-self,ding2024cycle}.
LeDex learns from trajectories connecting code explanation and refinement, and OpenCodeInterpreter integrates generation, execution, feedback, and iterative revision in an open code system \cite{jiang2024ledex,zheng-etal-2024-opencodeinterpreter}.
These methods are directly relevant to repair, but their feedback channels provide information that is unavailable when a model receives only the task specification, its Initial Candidate, and self-generated intermediate artifacts.

Other systems make the execution signal more granular.
Revisit Self-Debugging analyzes bias in self-generated tests and compares post-execution feedback with debugging based on intermediate runtime states \cite{chen-etal-2025-revisit}.
LDB verifies basic-block runtime states step by step to localize and explain faults, whereas TraceCoder uses execution traces for multi-agent diagnosis, repair, and rollback \cite{zhong-etal-2024-debug,huang2026tracecoder}.
Such state and trace information can guide fault localization, but it also makes these systems different from execution-feedback-free Self-Refinement.

Staged workflows also appear in candidate selection and agent-based code generation.
CodeT selects candidates using generated tests and execution agreement, while LEVER reranks candidates with a learned verifier that consumes execution results rather than revising a single candidate \cite{chen2023codet,pmlr-v202-ni23b}.
AgentCoder separates code generation, test generation, and execution among agents, and MapCoder organizes retrieval, planning, coding, and debugging as a multi-agent workflow \cite{huang2023agentcoder,islam-etal-2024-mapcoder}.
At repository scale, RepairAgent uses an autonomous repair workflow and Agentless reduces the workflow to localization, repair, and validation \cite{bouzenia2025repairagent,xia2024agentless}.
These systems establish that additional stages can distribute specialized responsibilities, but their tool use, multiple agents, candidate selection, or repository interaction prevents a direct attribution of gains to same-model Critique Generation or Revision Planning.

The value of additional stages also depends on their inference cost.
Olausson et al. compare the allocation of a fixed budget to repair calls and independent resampling, finding that repair is not consistently more effective when the model cannot diagnose its own failing code reliably \cite{olausson2024selfrepair}.
This work motivates evaluating additional calls against their cost, although its repair setting centers on failing candidates and execution feedback rather than paired outcomes for all initial candidates.
For locally deployed 1B to 3B models, Feedback Over Form reports that execution feedback and early stopping can matter more than workflow topology, and that text-only refinement did not improve performance in its preliminary condition \cite{mcandrews2026feedback}.
Its local-model scope is close to ours, but it does not isolate the correctness and token effects of cumulatively adding critique and planning to a shared Initial Candidate.

\subsection{Preservation, Selective Refinement, and the Research Gap}

Refinement can damage an initially correct program as well as repair an incorrect one.
CoCoS makes this tradeoff explicit by treating correction and preservation as joint objectives and by reporting both repair and regression transitions \cite{cho-etal-2025-self}.
Its evidence shows why final pass rate alone is insufficient, but it does not evaluate separately prompted Critique Generation, Revision Planning, or Refinement-Need Decision stages.
CodeChat-Eval evaluates externally requested multi-turn code changes and observes that Functional Correctness can deteriorate as revision dialogues continue \cite{guo2026codechateval}.
It provides direct evidence of a preservation problem in code editing, although the revisions respond to developer instructions rather than self-generated judgments about the Initial Candidate.
Jin and Chen find that LLM-based code reviewers can falsely reject correct implementations because of hallucinated requirements and unsupported concerns \cite{jin2026reliable}.
This overcorrection is relevant to a Refinement-Need Decision because a false defect judgment can trigger unnecessary refinement, while a review verdict alone does not establish a Correct-to-Incorrect Regression in revised code.

Selective computation offers one possible response to this tradeoff.
ReVISE integrates intrinsic verification with a learned choice to continue or stop refinement \cite{pmlr-v267-lee25ab}.
RubricRefine instead performs training-free, pre-execution review of tool-use code with explicit rubrics and revises the code when the review identifies a problem \cite{levine2026rubricrefine}.
Both approaches connect self-assessment to conditional refinement, but neither isolates a standalone Decision whose \texttt{PRESERVE} outcome returns the exact Initial Candidate and whose consequences can be separated into Prevented Regression and Missed Repair.
Candidate-selection methods such as CodeT and LEVER preserve a preferred generated candidate through test- or verifier-based ranking rather than through post-generation Self-Refinement \cite{chen2023codet,pmlr-v202-ni23b}.
They provide adjacent evidence for allocating computation selectively, but rely on multiple candidates and execution-derived evidence.

The literature therefore addresses same-model feedback, trained self-correction, execution-guided debugging, selective verification, staged agents, functional regression, and inference cost in largely separate settings.
Evidence remains limited on how these concerns interact when locally deployable open-weight instruct models refine code without execution or external verifier feedback and without model training.
In particular, prior work has not jointly used a Shared-Initial Design to compare Direct Revision, Critique-Conditioned Revision, and Critique-and-Plan-Conditioned Revision as cumulative Stage Compositions; measured Repair and Correct-to-Incorrect Regression for the same initial candidates; distinguished Prevented Regression from Missed Repair under a standalone Refinement-Need Decision; and accounted for the token consumption of each stage.

This study addresses that gap through an inference-only comparison in which each protocol begins from the same Self-Generated Initial Candidate and uses the same locally deployable open-weight instruct model for every Refinement Stage.
The comparison adds Critique Generation and Revision Planning incrementally to Code Revision while withholding execution results, compiler diagnostics, traces, and external verifier feedback from the model.
Candidate-level Functional Correctness transitions reveal whether each protocol repairs initially incorrect code or damages initially correct code, and Decision-Conditioned Refinement reveals the tradeoff between exact preservation and lost repair opportunities.
Stage Token Cost is considered alongside these outcomes to characterize when additional protocol structure is useful rather than assuming that more model calls are inherently beneficial.
