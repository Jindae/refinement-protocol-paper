\section{Background}

Self-Refinement improves an Initial Candidate through one or more subsequent model calls.
Self-Refine established a general pattern in which the same large language model (LLM) generates an output, produces natural-language feedback, and revises the output without additional training \cite{madaan2023selfrefine}.
In code generation, Self-Debugging uses natural-language code explanations and, when tests are available, execution results to guide iterative revision \cite{chen2024selfdebug}.
We use Self-Refinement in a narrower sense: the same model reviews and revises its Self-Generated Initial Candidate using only the task specification and self-generated intermediate artifacts, while tests are reserved for post-hoc evaluation and no Execution Feedback is provided to the model.

\subsection{Challenges and Risks of Code Self-Refinement}

An additional refinement call does not necessarily produce a better program.
Olausson et al. compare repair with independent resampling under a fixed inference budget and find that repair can be ineffective when a model cannot diagnose its own failing code reliably \cite{olausson2024selfrepair}.
For locally deployed small models, Feedback Over Form similarly reports that execution feedback and early stopping can matter more than workflow topology, while text-only refinement did not improve performance in its preliminary condition \cite{mcandrews2026feedback}.
Although both studies emphasize settings with execution feedback, they motivate evaluating whether the benefits of additional refinement calls justify their cost.

Refinement can also damage an initially correct program.
CoCoS treats correction and preservation as joint objectives and distinguishes incorrect-to-correct repairs from correct-to-incorrect regressions \cite{cho-etal-2025-self}.
This transition-based view is close to our analysis, but CoCoS trains a correction-preserving model rather than comparing inference-time protocols over the same Initial Candidate.
CodeChat-Eval provides complementary evidence by showing that Functional Correctness can deteriorate over externally directed multi-turn code revisions \cite{guo2026codechateval}.
Its revisions follow developer instructions rather than self-generated critique, but the observed regressions demonstrate that more editing is not inherently beneficial.

A refinement system must therefore decide not only how to revise a candidate, but also whether the candidate should be revised.
Jin and Chen show that LLM-based code reviewers can falsely reject correct implementations because of hallucinated requirements and unsupported concerns \cite{jin2026reliable}.
Such overcorrection may trigger unnecessary refinement, although a false review verdict does not by itself establish a Correct-to-Incorrect Regression in the revised code.
Revisit Self-Debugging also identifies bias in self-generated tests, showing that even apparently informative feedback may provide an unreliable basis for repair \cite{chen-etal-2025-revisit}.
These findings motivate paired analysis of Repair, Correct-to-Incorrect Regression, and exact preservation instead of relying only on final pass rate.

\subsection{Methods for Improving Code Self-Refinement}

One family of methods improves refinement through explicit critique or reflection.
RCO trains a critic with a critique-utility reward derived from the improvement of an actor's revised response, avoiding direct critique-preference assessment \cite{yu-etal-2025-training}.
SCOPE produces structured critiques consisting of subgoals, gap analysis, and robustness checks before revision \cite{zhang2026scope}.
Broader reflection systems convert task feedback into verbal episodic memory or coordinate safety- and helpfulness-oriented critics equipped with external knowledge and tools \cite{shinn2023reflexion,le2024indict}.
These methods support the idea that an explicit critique or reflection artifact can guide subsequent decisions, but they use trained critics, external signals and tools, or integrated agent loops rather than isolating the effect of adding Critique Generation and Revision Planning to a fixed model.

Other methods learn correction behavior or structure pre-execution review.
SCoRe uses multi-turn online reinforcement learning over self-generated correction traces, CoCoS trains small models to maintain correct outputs while correcting incorrect ones, and ReflexiCoder internalizes an initial-generation, reflection, and correction trajectory that operates without an execution engine at inference time \cite{kumar2025score,cho-etal-2025-self,jiang-etal-2026-reflexicoder}.
ReVISE trains intrinsic self-verification and reasoning correction through a preference-learning curriculum, while RubricRefine generates task-specific rubrics to score and iteratively repair tool-use code before execution \cite{pmlr-v267-lee25ab,levine2026rubricrefine}.
These approaches show that correction and verification can be learned or structured, but their integrated procedures do not expose the incremental correctness and token effects of separate inference-time Refinement Stages.
Code Reffix uses a dual-task protocol to evaluate reflection separately from reflection-guided repair, CodeReviewQA decomposes review comprehension into change-type recognition, change localization, and solution identification, and COAST evaluates bug localization, identification, repair, and recognition while using agent-generated data for training \cite{di-etal-2026-code,lin-etal-2025-codereviewqa,yang-etal-2025-coast}.
These decompositions provide indirect support for Stage Composition, while focusing on capability evaluation or training rather than Shared-Initial protocol comparison.

A second family improves refinement with Execution Feedback.
Self-Edit supplies example-test execution results to a fault-aware editor, CYCLE learns self-refinement from feedback including test-suite results, LeDex trains on explanation-and-refinement trajectories filtered by execution, and OpenCodeInterpreter combines generation and execution with execution and human feedback for iterative refinement \cite{zhang-etal-2023-self,ding2024cycle,jiang2024ledex,zheng-etal-2024-opencodeinterpreter}.
More detailed signals are used by LDB, which verifies basic-block runtime states, and TraceCoder, which performs trace-driven diagnosis, repair, and rollback \cite{zhong-etal-2024-debug,huang2026tracecoder}.
CodeT and LEVER instead use generated tests or execution-aware verification to select among candidates rather than revise one Initial Candidate \cite{chen2023codet,pmlr-v202-ni23b}.
These methods demonstrate the value of behavioral evidence for debugging, but their results cannot determine how well a model refines code without execution feedback or external verification.

Multi-agent and repository-level systems place refinement within broader workflows: AgentCoder separates programming, test design, and test execution; MapCoder separates example recall, planning, coding, and debugging; RepairAgent autonomously selects tools for program repair; and Agentless reduces repository repair to localization, repair, and patch validation \cite{huang2023agentcoder,islam-etal-2024-mapcoder,bouzenia2025repairagent,xia2024agentless}.
Their stage and resource tradeoffs therefore include execution or repository interaction that is absent from our fixed-candidate setting.
Other adjacent work studies interactive coding environments, iterative model improvement, semantic reasoning, tool-interactive critiquing, efficiency optimization, function decomposition, hardware-description generation, and thought-level search \cite{yang2023intercode,zhou2025refinecoder,ding2024semcoder,gou2024critic,huang2024effilearner,chen2024funcoder,niu2025rechisel,li-etal-2025-rethinkmcts}.
Repository interfaces, multilingual debugging, code-hallucination detection, and low-resource-language curricula further broaden the literature but do not directly compare inference-time revisions of the same candidate \cite{yang2024sweagent,liu-etal-2026-mdeval,andriushchenko-etal-2026-efficient,wen-etal-2026-coderise}.

Existing studies therefore establish that refinement may repair or regress code and that critique, training, selective verification, and Execution Feedback can improve parts of the process, but evidence remains limited for inference-only Self-Refinement by locally deployable open-weight instruct models under a strict no-feedback condition.
In particular, none of the reviewed studies jointly uses a Shared-Initial Design to compare Revision alone, Critique followed by Revision, and Critique followed by Plan and Revision as cumulative Stage Compositions; measures Repair and Correct-to-Incorrect Regression for the same candidates; evaluates whether a standalone Refinement-Need Decision prevents regressions or misses repairs; and accounts for the token consumption of each stage.
This study addresses that gap by applying the same model to the same Initial Candidate across all protocols, incrementally adding Critique and Plan before Revision, and withholding execution feedback.
The resulting comparison characterizes the correctness and token-cost tradeoffs of protocol structure and Decision-Conditioned Refinement before the following section formalizes the experimental design.
